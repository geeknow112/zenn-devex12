## この記事で得られること

- Claude Codeの `.claude/settings.json` / `settings.local.json` の権限設定を編集したとき、**セッションを再起動しなくても効くケースと効かないケース**があった実体験
- `allow` リストへの追加と `deny` リストからの削除で、挙動が違って見えた2つの検証記録
- 権限プロンプトの詰まり（通称「Yes地獄」）に遭遇したときの切り分け方

数字で殴る系の検証記事ではなく、実際に2つの別セッションで踏んだ「効いた／効かなかった」の実体験ベースの記録です。母数は2件なので、これが一般的な仕様と断定するものではありません。

## 背景

Claude Codeでは、Bashコマンドやツールの実行許可を `.claude/settings.json`（プロジェクト共有）と `settings.local.json`（個人ローカル）の `permissions.allow` / `permissions.deny` で制御できます。

これを**セッションの途中で編集した場合、いつから効くのか**がずっと曖昧でした。ドキュメントを読んでも明言されておらず、実際に2回、別の状況で検証する機会があったので記録します。

## 検証1: allowリストへの追加（2026-07-30）

夜間の無人バッチ処理（記事下書き自動生成タスク）を回している最中、Bashコマンドの実行許可プロンプトが何度も出て停止する、いわゆる「Yes地獄」に遭遇しました。そこで以下を**セッションを止めずに**順番に試しました。

1. `.claude/settings.json` に `defaultMode: "acceptEdits"` ＋ denyリストを追加
2. `/permissions` コマンドで設定リロードを試行
3. 特定のgitコマンドを個別に `allow` リストへ追加
4. 最終手段として `"Bash"` の**ブランケット許可**（全Bashコマンドを許可）を `allow` に追加

結果、**どれもセッション中には反映されませんでした**。プロンプトは同じセッションが続く限り出続け、次にセッションを開始し直して初めて設定が効いていることを確認しました。

## 検証2: denyリストからの削除（2026-08-08）

別の日、Qiita/Zennへの記事PR作成作業中に `git push` を実行しようとしたところ、拒否されました。原因は `.claude/settings.json` と `settings.local.json` の両方に、以下の**明示的な拒否ルール**が入っていたことでした。

```json
{
  "permissions": {
    "deny": ["Bash(git push:*)"]
  }
}
```

チャットで「許可する」と伝えるだけでは通らず（ハードな拒否ルールは対話的な承認では上書きされない）、設定ファイル自体を編集する必要がありました。そこで、同じセッション内で以下を行いました。

1. 両方の設定ファイルから `Bash(git push:*)` を `deny` リストから削除
2. `settings.local.json` の `allow` リストに `Bash(git push *)` を追加

そのまま**同じセッションで**もう一度 `git push` を実行したところ、**再起動なしで成功**しました。

## 2つの結果を比べる

| 検証 | 変更内容 | セッション再起動 | 結果 |
|---|---|---|---|
| 検証1（2026-07-30） | `allow`への追加（個別ルール＋ブランケット`"Bash"`） | なし | ❌ 効かなかった |
| 検証2（2026-08-08） | `deny`からの削除＋`allow`への追加 | なし | ✅ 即反映された |

同じ「設定ファイルの編集」でも、結果が違いました。

## なぜ結果が違ったのか：2つの仮説

Claude Codeの権限まわりの実装は非公開なので確定はできませんが、考えられる仮説を2つ挙げます。

**仮説A: allowとdenyで評価タイミングが違う**
`deny` はツール呼び出し前の**即時ブロックチェック**（ファイルを都度読みに行く、または軽量なブロックリストとして扱われる）、`allow` は**セッション開始時に確定するプロンプトポリシー**（一度計算してセッション中はキャッシュする）という設計なら、今回の2件の結果と矛盾しません。

**仮説B: 変更した項目の種類（削除 vs 追加）で挙動が違う**
`deny` からの「削除」は安全側に倒す変更（許可が広がる方向）なので即時反映を許し、`allow` への「追加」も同じく許可が広がる方向のはずなので、この仮説だけでは検証1の結果を説明しきれません。仮説Aの方が今回の観測結果には整合的に見えます。

いずれにせよ、2件のサンプルからの推測でしかない点は強調しておきます。

## 再現してみたい人向けの手順

同じ環境がある人は、以下の手順で自分でも検証できます。結果が違ったら、ぜひコメントで教えてください。

```bash
# 1. プロジェクトの .claude/settings.json に deny ルールを1つ追加
#    (例: 普段使わない安全なコマンドを選ぶ。git push は影響が大きいので避ける)
echo '{"permissions":{"deny":["Bash(echo hello-deny-test:*)"]}}' > .claude/settings.json

# 2. セッションを開始し、そのコマンドが拒否されることを確認
#    (Claude Codeに `echo hello-deny-test` を実行させる)

# 3. セッションを止めずに、.claude/settings.json から該当のdenyルールを削除

# 4. 同じセッション内で、同じコマンドをもう一度実行させてみる
#    → 即反映されるか、次のセッションまで拒否され続けるかを記録
```

同様に `allow` 側も、未許可コマンド→プロンプト待ち→`allow`に追加→再実行、という手順で試せます。OS・Claude Codeのバージョン・セッションの種類（対話 vs バックグラウンド）によって結果が変わる可能性もあるので、その辺りの条件も併せて記録しておくと比較しやすくなります。

## 実務での切り分け方

同じ経験をした場合の、現実的な対処法をまとめます。

- Bashコマンドが**明示的に拒否されている**（`deny`に一致するルールがある）場合は、そのルールを消せば同じセッション中に直る可能性がある
- プロンプトが単に**許可されていないだけ**（`allow`に無い）で毎回Yes/No待ちになる場合は、`allow`を足してもそのセッション中は直らない前提で動く
- 無人バッチ処理を回す予定があるなら、**着手前**に`allow`設定を固めてからセッションを開始する
- 「設定を変えたのに直らない」ときは、まず対象のコマンドが`deny`側の話か`allow`側の話かを切り分けると原因の見当がつけやすい

## まとめ

- Claude Codeの権限設定変更が「いつ効くか」は、`allow`追加と`deny`削除とで体感が違った
- `deny`ルールの削除は即座に反映された（1件）が、`allow`ルールの追加はセッション再起動まで反映されなかった（1件）
- 断定はできないので、無人実行を計画するときは「設定は事前に固めておく」のが最も安全
