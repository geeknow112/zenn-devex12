## この記事で得られること

- リポジトリ直下にルールファイル（`.kiro/steering/` のような、いわゆる「AGENTS.md的なもの」）を置いても、AIコーディングエージェントがそれを無視した**実際の2件の事例**
- 「記憶（メモリ）に書いてある」ことと「毎セッション自動で読み込まれるファイルに書いてある」ことの効き方の違い
- 同じ失敗を3回目起こさないために、実際にどう設定を変えたか

数字で殴るタイプの検証ではなく、実際に自分の開発環境で2回続けて踏んだ「AIがルールを守らなかった」実例の記録です。

## 背景：なぜルールファイルを置いたか

個人開発でZenn/Qiitaへの技術記事執筆をAIエージェント（Claude Code）に任せる運用をしています。記事の品質を保つため、リポジトリ直下の `.kiro/steering/media-update.md` に以下のようなルールを明文化していました。

- 一般論だけのゴミ記事は書かない
- 「一球入魂で1000PV狙える記事」を書く
- 独自の視点・実体験、具体的な数字を必ず入れる

さらに `user-preferences.md` には、GitHub操作は独自CLIツール（`biz-tools media draft/publish`）経由で行い、手動でgit操作しないというルールも書いていました。

これらは「エージェントに毎回読ませれば守られる」はずのルールでした。実際には2回、無視されました。

## 事例1（2026-08-01〜08-02）：夜間バッチで量産されたゴミ記事

無人の夜間バッチ処理で、Zenn/Qiitaにそれぞれ5本ずつ、Cloudflare Workers・direnv・MCP・mise-asdf・Pactといったテーマで記事を自動生成させました。

出来上がったのは、どれも「ネットで一般的に言われていることをまとめただけ」の記事でした。個人の実体験も具体的な数字も入っていませんでした。品質基準を明文化したファイルがリポジトリに存在していたにもかかわらず、です。

結果、該当するPR（Zenn #25〜27、Qiita #17〜19）はすべてクローズになりました。原因を遡ると、**そもそも作業開始前に `.kiro/steering/` を読んでいなかった**ことに行き着きました。

## 事例2（2026-08-08）：同じ失敗を、同じ日にもう一度

事例1の教訓は、AIエージェント側の「記憶」機能（セッションをまたいで参照される、関連度に応じて呼び出されるメモファイル）に記録していました。「作業前に `.kiro/steering/` を必ず確認する」という記憶です。

にもかかわらず、6日後の別セッションで、Zenn/Qiitaのトレンドを調べて記事を1本ずつ下書き→PR作成する作業をした際、**また `.kiro/steering/` を確認せずに進めました**。結果:

- 記事の分量が薄く、独自の数字もほぼ無い状態でPRを作成
- GitHub操作もルールに反して手動 `git push` / `gh pr create` で実施

ユーザーから「文章量が少ないな。あとPV1000とか狙えなさそうじゃん。この辺りのルール決めてたでしょ？」と指摘されて初めて気づき、慌てて `.kiro/steering/` を読み直す、という流れになりました。

## なぜ「記憶」だけでは守られなかったのか

推測ですが、AIエージェントの「記憶」機能は、**そのセッションの文脈に関連度が高いと判断された記憶だけ**が呼び出される設計になっていることが多いです。「Qiita/Zennのトレンドを調べて記事を書く」という作業指示から、「`.kiro/steering/` を確認する」という記憶が毎回確実に呼び出される保証はありませんでした。

一方、`CLAUDE.md`（Claude Codeの場合）のような、**セッション開始時に無条件で読み込まれるファイル**に同じ内容を書けば、関連度判定を経由しないため、原理的には読み飛ばされにくくなります。

## 実際にやった対処

2回目の事故のあと、以下の対応をしました。

1. `.kiro/steering/` の内容を要約した記憶ファイルを更新し、「2026-08-02と2026-08-08の2回、確認漏れが起きた」という事実を明記
2. リポジトリ直下に `CLAUDE.md` を新規作成し、「記事作業の前に `.kiro/steering/` を必ず読む」というルールを直接書き込んだ

まだ「これで3回目が起きないか」は検証できていません（当然ながら、これを書いている記事自体が事例2の反省を踏まえて `.kiro/steering/` を確認した上で書かれています）。次に同種の作業をする機会があれば、CLAUDE.md昇格後に同じミスが起きるかどうかを追記する予定です。

## この記録から言えること

- ルールを「エージェントの記憶」にだけ置くのは、少なくとも2回中2回、作業開始前のチェックとしては機能しなかった
- 「毎回無条件で読み込まれる場所」と「関連度に応じて呼び出される場所」は、同じ内容を書いても効き方が違う可能性がある
- ルールファイルを置いた「だけ」で安心せず、実際に守られているかを事後にログで確認する運用が必要だった

## まとめ

- リポジトリにルールファイルを置いても、AIエージェントは少なくとも自分の環境では2回連続でそれを読み飛ばした
- 原因は「記憶」への記録だけに頼っていたことで、関連度判定に依存しない場所（CLAUDE.md）への格上げで対処を試みた
- 効果測定はこれから。同じ轍を踏んだ・踏まなかった事例があれば知りたい

※本記事は個人環境（Windows / Claude Code CLI）での2件の実体験の記録です。エージェントの内部実装は非公開のため、原因分析の部分は推測を含みます。
