## この記事の位置づけ

前回の記事では「質問攻めを止める」ためのSteering設定を紹介しました。

https://zenn.dev/geeknow112/articles/kiro-steering-real-workflow

今回はその続編として、**Kiroを「完全オート」で動かす設定**を解説いたします。

## 目標：ここまで自動化したい

```
私：「作業を進めて」
Kiro：（memoを読む）
Kiro：（ブランチ作成）
Kiro：（ファイル編集）
Kiro：（テスト実行）
Kiro：（lint実行）
Kiro：（コミット）
Kiro：（push）
Kiro：（PR作成）
Kiro：「完了しました。PR: https://...」
```

**途中で承認を求めない。質問もしない。結果だけ返す。**

これを実現するための設定を公開します。

## 3つの仕組みを組み合わせる

Kiroの「完全オート」は、3つの機能の組み合わせで実現します。

| 機能 | 役割 |
|------|------|
| **Autopilot** | ファイル編集・コマンド実行を自動で進める |
| **Steering** | 「質問するな」「この手順で進めろ」を指示 |
| **Hooks** | 特定のタイミングで自動処理を差し込む |

それぞれ単体では不完全ですが、組み合わせると強力です。

## 設定1：Autopilotを有効化する

まず大前提として、AutopilotモードをONにします。

チャット欄の上部にあるトグルスイッチで切り替えできます。

```
[Autopilot: ON] ← これ
```

**Autopilot = ON の状態では、ファイル編集のたびに承認を求めません。**

変更は自動で適用され、あとから「View all changes」「Revert」で確認・取り消しができます。

:::message alert
Autopilotは強力ですが、間違った変更も自動適用されます。Gitで管理されたプロジェクトで使うことを強く推奨します。
:::

## 設定2：Steeringで「判断基準」を与える

Autopilotだけでは、Kiroは「何をすればいいか」がわかりません。結局質問してきます。

そこでSteeringで**判断基準**を与えます。

```markdown:full-auto-workflow.md
---
inclusion: manual
---

# 完全自動ワークフロー

`#full-auto` で呼び出された場合、以下のルールで作業を進める。

## 基本方針
- **質問しない**。memoと既存コードから推論する
- **承認を求めない**。必要な作業はすべて実行する
- **完了まで止まらない**。エラーが出たら自力で修正する

## 情報の取得先
1. `memo/memo.YYYYMMDD.md` で当日のタスクを確認
2. 前回のコミット履歴で作業の続きを把握
3. 既存コードのパターンに従う

## 作業完了の定義
- コードが動作する状態
- テストがパスする
- lintエラーがない
- PRが作成されている（push可能な場合）

## エラー時の対応
- ビルドエラー → 修正して再試行（最大3回）
- テスト失敗 → 失敗内容を分析して修正
- 3回試行しても解決しない → その時点での状態を報告して停止
```

### ポイント解説

**「質問しない」を明記する**

AIは親切心で確認してきます。「本当にこれでいいですか？」と。これを止めるには明示的に書く必要があります。

**「エラー時の対応」を書く**

書かないと、エラーが出た時点で「どうしますか？」と聞いてきます。自己解決のルールを与えておくことで、止まらなくなります。

**「完了の定義」を書く**

ゴールが曖昧だと「これで終わりでいいですか？」と確認してきます。完了条件を明確にすることで、自動的に終点を判断できます。

## 設定3：Hooksで「常に実行する処理」を自動化

Steeringだけでは、Kiroが「テストを実行する」「lintを実行する」を忘れることがあります。

Hooksを使うと、**特定のタイミングで自動的に処理を差し込めます**。

### ファイル保存時に自動lint

```json:.kiro/hooks/lint-on-save.json
{
  "name": "Lint on Save",
  "version": "1.0.0",
  "when": {
    "type": "fileEdited",
    "patterns": ["*.ts", "*.tsx", "*.js", "*.jsx"]
  },
  "then": {
    "type": "runCommand",
    "command": "npm run lint:fix"
  }
}
```

### PR作成前にテスト実行

```json:.kiro/hooks/test-before-pr.json
{
  "name": "Test Before PR",
  "version": "1.0.0",
  "when": {
    "type": "preToolUse",
    "toolTypes": ["shell"]
  },
  "then": {
    "type": "askAgent",
    "prompt": "git push または PR作成の前に、テストが全てパスしていることを確認してください。パスしていない場合は先にテストを修正してください。"
  }
}
```

### タスク完了時の確認

```json:.kiro/hooks/verify-on-complete.json
{
  "name": "Verify on Complete",
  "version": "1.0.0",
  "when": {
    "type": "agentStop"
  },
  "then": {
    "type": "askAgent",
    "prompt": "作業が完了した場合、以下を確認して報告してください：1) 変更ファイル一覧 2) テスト結果 3) 次のアクション（PR URLまたは残作業）"
  }
}
```

## 実際の動作例

設定完了後の動作を示します。

```
私：#full-auto 作業を進めて

Kiro：memo/memo.20260620.md を確認します。

Kiro：本日のタスク「認証機能のリファクタリング」を確認しました。
      前回のコミット履歴から、auth/login.ts の修正途中であることを把握しました。
      作業を続行します。

Kiro：[ファイル編集: auth/login.ts]
Kiro：[ファイル編集: auth/types.ts]
Kiro：[Hook実行: lint-on-save]

Kiro：[コマンド実行: npm run test]
      Tests: 23 passed, 0 failed

Kiro：[コマンド実行: git add -A && git commit -m "refactor: 認証ロジックを整理"]
Kiro：[コマンド実行: git push -u origin feature/auth-refactor]
Kiro：[コマンド実行: gh pr create --title "認証機能のリファクタリング" --body "..."]

Kiro：作業完了しました。
      - 変更ファイル: auth/login.ts, auth/types.ts
      - テスト: 全パス
      - PR: https://github.com/.../pull/42
```

**私の入力は1回だけ。あとは結果報告まで自動。**

## トラブルシューティング

### 「それでも質問してくる」場合

Steeringの指示が弱い可能性があります。より強い表現に変えてみてください。

```markdown
# NG: 弱い表現
- できれば質問せずに進めてください

# OK: 強い表現
- **質問は禁止**。不明点は推論で補う
- 確認が必要な場合でも、まず実行してから報告する
```

### 「途中で止まる」場合

エラー処理のルールが不足しています。想定されるエラーパターンを追記してください。

```markdown
## エラー時の対応（追記）
- 依存関係エラー → `npm install` を実行
- 型エラー → 型定義を修正
- 権限エラー → 報告して停止（自力解決しない）
```

### 「暴走して困る」場合

Hooksで安全装置を入れてください。

```json:.kiro/hooks/safety-check.json
{
  "name": "Safety Check",
  "version": "1.0.0",
  "when": {
    "type": "preToolUse",
    "toolTypes": ["shell"]
  },
  "then": {
    "type": "askAgent",
    "prompt": "以下のコマンドは禁止です：rm -rf, git push -f, DROP TABLE。これらを実行しようとしている場合は中止してください。"
  }
}
```

## 活用例：巨大リポジトリの調査

完全オートが最も威力を発揮するのは、**巨大リポジトリの調査**です。

### なぜ調査タスクと相性がいいのか

- ファイル探索・grep・依存関係追跡は「確認」しても意味がない
- 途中で「このファイルも見ますか？」と聞かれると思考が中断される
- 結果（レポート）が出るまで止まらず進んでほしい

### 調査用Steering

```markdown:investigate-repo.md
---
inclusion: manual
---

# リポジトリ調査モード

`#investigate` で呼び出された場合、以下のルールで調査を進める。

## 基本方針
- **質問しない**。調査対象を自分で判断する
- **網羅的に調べる**。関連しそうなファイルはすべて確認する
- **レポートにまとめる**。調査結果は構造化して出力する

## 調査の進め方
1. まずディレクトリ構造を把握する
2. エントリーポイント（main, index, app）から追跡する
3. 依存関係を再帰的に辿る
4. 設定ファイル（config, env, yaml）も確認する
5. テストコードからも仕様を読み取る

## レポートの形式
調査完了後、以下の形式でレポートを出力する：

### 1. 概要
- 対象機能の目的
- 主要なファイル一覧

### 2. アーキテクチャ
- データフロー
- 依存関係

### 3. 重要な実装詳細
- 核となるロジック
- 注意すべき点

### 4. 関連ファイル一覧
- ファイルパスと役割の対応表

## 出力先
- 調査結果は `memo/investigation-YYYYMMDD-{対象}.md` に保存
```

### 実際の使用例

```
私：#investigate 認証周りの実装を調査して

Kiro：ディレクトリ構造を確認します。
Kiro：src/auth/ 配下に認証関連のコードを発見しました。
Kiro：エントリーポイント src/auth/index.ts から追跡します。
      ...
Kiro：（50ファイル以上を自動探索）
      ...
Kiro：依存関係の追跡が完了しました。
Kiro：設定ファイル config/auth.yaml を確認します。
Kiro：テストコード tests/auth/ から仕様を確認します。
      ...
Kiro：調査完了しました。
      レポートを memo/investigation-20260620-auth.md に出力しました。

      【概要】
      - JWT + Refresh Token方式の認証
      - 主要ファイル: 12ファイル
      
      詳細はレポートをご確認ください。
```

**私の入力は1回。あとは100ファイル以上を自動で調査してレポート生成まで完了。**

### 調査が特に有効なケース

- 新しく参加したプロジェクトの理解
- レガシーコードの把握
- 「この機能どこで実装されてる？」の調査
- リファクタリング前の影響範囲調査
- セキュリティレビューの事前調査

### 調査用Hooksの追加

大規模調査では時間がかかるため、進捗を報告させるHookがあると安心です。

```json:.kiro/hooks/investigation-progress.json
{
  "name": "Investigation Progress",
  "version": "1.0.0",
  "when": {
    "type": "postToolUse",
    "toolTypes": ["read"]
  },
  "then": {
    "type": "askAgent",
    "prompt": "10ファイル以上読み込んだ場合、現在の調査進捗（確認済みファイル数、残りの見込み）を簡潔に報告してください。"
  }
}
```

## 完全オートが向く作業・向かない作業

### 向く作業
- **巨大リポジトリの調査**（最も効果的）
- 定型的なコード生成（CRUD、テスト追加）
- リファクタリング（命名変更、構造整理）
- ドキュメント更新
- 依存関係の更新

### 向かない作業
- 設計判断が必要な新機能開発
- セキュリティに関わる変更
- 本番環境への操作
- 複数人が同時に触るファイルの変更

## まとめ

Kiroを「完全オート」にするための設定は以下の3点です。

1. **Autopilot ON** で承認スキップ
2. **Steering** で判断基準を与える
3. **Hooks** で自動処理を差し込む

前回の「質問攻めを止める」設定と組み合わせることで、**本当の意味での自動化**が実現できます。

設定ファイルは最初の1時間で作れます。1週間使えば元が取れるので、ぜひ試してみてください。
